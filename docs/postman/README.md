# Postman Demo

These collections demonstrate the Smart Clinic System’s appointment and billing flows. Each collection includes request descriptions and saved response examples.

You can inspect the saved examples without running the application. To execute the requests, follow the setup below.

## Setup

1. Start the application and its required infrastructure using the [main README](../../README.md).
2. Import the six collection JSON files and the environment JSON from this folder into Postman.
3. Select the **Smart Clinic System - local** environment.
4. Verify the service addresses:

   | Variable | Default value |
   | --- | --- |
   | `scheduling_url` | `http://localhost:8080` |
   | `billing_url` | `http://localhost:8081` |

Generated identifiers and payment values are intentionally empty in the template. Request scripts populate them as you execute the flows.

For payment and refund scenarios, configure Billing with Stripe test credentials and keep webhook forwarding active. The Stripe CLI must use the same Stripe test account or sandbox as Billing.

## Collections

| Collection | Demonstrates |
| --- | --- |
| Booking flow | Configure a doctor’s schedule and billing profile, book an appointment, and retrieve its draft invoice. Includes validation error examples. |
| Payment flow | Prepare and initiate payment, simulate successful or declined payments through Stripe, and inspect payment and invoice states. |
| Cancellation flow | Cancel an appointment as a patient and inspect the resulting invoice state, including an eligible refund. |
| System cancels appointments | Cancel affected appointments by adding doctor unavailability or changing a working schedule. |
| Reschedule appointment | Move an appointment to another available slot and inspect the original and replacement invoices. |
| Expiration flow | Observe an unpaid appointment becoming `CANCELLED` and its invoice becoming `EXPIRED` after the expiry cutoff. |

## Running the Scenarios

Start with **Booking flow**, then use **Payment flow** for the successful payment walkthrough.

Treat cancellation, system cancellation, rescheduling, and expiration as separate scenarios. Prepare a fresh appointment through the Booking flow for each one, and pay for it first when demonstrating a paid scenario.

Run requests manually in the order described by each collection. Some steps require a Stripe CLI command, waiting for background processing, or choosing between alternative scenarios.

Before sending requests:

- Update the fixed dates in request bodies. Choose a valid schedule start date and future appointment dates that match the doctor’s working hours.
- Adjust unavailability periods and schedule changes to overlap the appointment you intend to affect.
- Check responses from “latest” queries to confirm they selected the intended appointment or invoice.
- Keep the selected appointment ID unchanged while checking that scenario’s results.

Saved response examples document previous runs; their identifiers and dates are illustrative.

## Payment and Billing Notes

“Draft invoice” and “proforma invoice” refer to the same invoice stage in this project. The API represents it as `DRAFT`.

The **Initiate payment** request description contains Stripe CLI instructions for simulating successful and declined payments. Use the PaymentIntent ID generated by your current request.

After a declined payment, the invoice can remain `PAYMENT_PENDING` while its existing payment window is active, preserving the quoted price for a retry. Once that window expires and background processing runs, it returns to `DRAFT`. The recorded demonstration uses a one-minute window.

For patient-initiated cancellation, a paid appointment is eligible for a refund when more than 24 hours remain before its start. Otherwise, the appointment is cancelled without a refund. Unpaid appointments are cancelled without a refund.

## Asynchronous Updates

Webhook handling, background jobs, and communication between services can delay the final state changes. If a query still shows an intermediate state, wait briefly and repeat the status query.

Keep credentials and payment client secrets out of committed environment files and saved examples.
